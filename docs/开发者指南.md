## 一、系统全貌

### 1.1 技术栈与进程模型

```
浏览器
  │
  ├── 前端容器（Next.js，App Router）
  │     └── /api/* 全部反向代理到后端容器
  │
  └── 后端容器（Go，标准库 http + gin 路由）
        ├── PostgreSQL（外部，不在 compose 里）
        └── 对象存储（S3 协议兼容，可选；不配则落本地磁盘）
```

两个容器、一个外部数据库。后端**不服务任何 HTML**，前端页面全部由 Next.js 容器提供。

一个直接影响排障的后果：**后端看到的连接来源恒为前端容器在 Docker 网络里的 IP**。所有 `/api/*` 都是前端转发过来的，所以后端拿不到浏览器真实 IP，除非把前端容器 IP 配进 `TRUSTED_PROXIES`。这一项配错会导致全站 IP 塌缩，进而让「登录失败锁定」变成任何人都能锁死任意账号的工具——部署说明里对此有详细警告，务必照做。

### 1.2 代码地图

**后端（module `aicanvas`）**

| 目录 | 文件数 | 职责 |
|---|---|---|
| `model/` | 22 | 纯数据结构：GORM 结构体、枚举、出参脱敏函数 |
| `repository/` | 28 | 唯一碰 GORM 的地方；事务、乐观锁都在这层 |
| `service/` | 53 | 业务规则 + 外部系统适配（AI 上游、对象存储、短信） |
| `handler/` | 45 | HTTP 入口：解析、校验、调用、响应 |
| `router/` | 1 | 全部路由注册，一个 `New()` 到底 |
| `middleware/` | 1 | 认证与权限 |
| `config/` | 2 | 环境变量加载 |

**前端（`web/src/`）**

| 目录 | 职责 |
|---|---|
| `app/` | Next.js App Router；`(user)` 与 `(admin)` 两个分组 |
| `components/` | 跨页面复用组件 |
| `lib/` | 纯逻辑：视频模式判据、模型类型判据、风格预设等 |
| `services/` | 与后端通信、本地存储、云同步 |
| `stores/` | 客户端状态（含持久化） |
| `constant/` | 价格估算、枚举、环境常量 |
| `hooks/` / `types/` | 复用 hook 与类型定义 |

### 1.3 启动流程

启动是一条**同步的直线**，下面每步跑完 HTTP 端口才开始监听。`main.go` 的 `bootStep()` 给每步计时，超过 500ms 会额外打一行警告。

| 步 | 做什么 | 关键位置 |
|---|---|---|
| 0 | 开日志落盘（默认 `data/logs/app.log`，32MB × 5 份轮转） | `applog.go` |
| 1 | 加载 `.env` → 解析环境变量 → `JWT_SECRET` 为空时**现场生成随机值** | `config/config.go` |
| 2 | **第一次连库**：选驱动、库不存在则自动建库、**AutoMigrate 24 张表**、创建默认管理员 | `repository/db.go`、`service/auth.go` |
| 3 | 渠道配置迁移（幂等） | `service/settings.go` |
| 4 | 模型类型回填：给没有元信息的模型按名字补 `kind` | `service/model_meta.go` |
| 5 | 拉起 7 个后台协程 | `main.go` |
| 6 | 恢复上次被杀时「已扣费、未拿到上游任务号」的视频提交 | `service/video_submit_recovery.go` |
| 7 | 开始监听 | `main.go` |

> ⚠️ **第 1 步的 `JWT_SECRET`**：不显式配置时每次重启都会生成新的随机密钥，**后果是所有人掉线**。生产环境必须显式配。
>
> ⚠️ **建表发生在第 2 步，不是第 1 步**。config 包不 import repository，第 1 步只加载配置、不碰数据库。排查「表怎么没建」时别看错地方。

**优雅停机窗口是 40 秒**（`main.go` 的 `shutdownGrace`）。取这个值是因为要等的是「已扣费、正在转发给上游」的请求。但 **Docker 默认 SIGTERM 后 10 秒强杀**，所以部署时必须配 `stop_grace_period`（compose）或 `--timeout ≥ 40`（手工 stop），否则这个窗口形同虚设——扣了钱的请求会被硬杀在半路。

### 1.4 后台常驻任务

启动时拉起 7 个后台协程。二次开发时若发现「某件事自己会发生」，多半是它们之一：

- **视频退款扫描器**（`handler/video_sweeper.go`）——定时查上游任务状态、给失败的退款、抢救「生成成功但没进画布」的孤儿成片。注意它住在 `handler` 包但和 HTTP 无关，按分层本该在 `service`。
- 其余包括模型元信息同步、媒体转码、提示词同步等，明细见 `main.go` 第 5 步那一段。

## 二、分层约定与破例

### 2.1 四层职责

依赖方向是单向的（已逐层扫描核对）：

- **model** 不 import 任何上层
- **repository** 不 import service
- **service** 不 import handler
- **service** 可以 import `net/http`（上游调用必需），但不认识 gin、不碰 `http.ResponseWriter`

几条具体约定：

- repository 每个函数自己取 `DB()`（懒初始化 + `sync.Once`），**没有接口、没有依赖注入、没有 mock**，测试直接打真 SQLite。
- 需要原子性的写操作封装成 `*Tx` 函数。**「扣费 + 记流水」必须在同一事务**是这个项目的硬规则。
- service 层用当前用户走 context 传递（`service/context.go` 的 `WithUser` / `UserFromContext`）。
- 允许展示给用户的错误文案用 `safeMessageError` 标记，其余错误一律不外泄。

### 2.2 一次请求怎么穿过这几层

**最规范的一条：异步图片生成**

```
POST /api/v1/generation-jobs
  → middleware.UserAuth
  → handler/generation_job.go  解析模型名与张数
  → service.ImageModelCostForUser      按档位算单价
  → service.SelectModelChannelForUser  预检渠道（配置问题立刻报错，不落库后失败）
  → service.CreateGenerationJob        扣费 + 落库
  → repository.SaveGenerationJob
  ← 立即返回任务 ID
  （后台 goroutine runGenerationJob 才真正调上游）
前端轮询 GET /api/v1/generation-jobs/:id
```

### 2.3 破坏分层的地方（接手必看）

**22 个 handler 文件直接调 repository，绕过 service。** 按调用点数量排：`sync.go` 27 处、`project.go` 22、`auth.go` 14、`group.go` 12、`user_report.go` 10……

实际含义：**同步、项目、分组、用户反馈、画布快照这几大块根本没有 service 层**，业务规则直接写在 handler 里。典型例子：

- 画布收缩护栏算法 → `handler/sync.go`
- 二级管理员数据隔离规则 → `handler/auth.go` 的 `applyL2SaveUserRules` / `l2OwnsGroup`

**二次开发要改这些功能，去 handler 找，去 service 翻会一无所获。**

另外 `middleware` 反向 import 了 `handler`（只为复用两个响应函数），这让依赖图出现一条回边。属可接受的小耦合，但要知道它存在。

## 三、无限画布

这是产品的核心，也是前端最复杂的部分。

### 3.1 数据同步：最该小心的一块

前端的画布数据通过 `POST /api/v1/sync/manifest` 整块推送到后端，存进 `sync_data` 表。这条路径**完全没有 service 层**，handler 直接调 repository。

链路上有三道保护，改动前必须理解它们为什么存在：

1. **512MB 体积闸**——请求体上限。
2. **「整项目消失」护栏**——本次推送相比云端少了整个项目时拒收。
3. **「大幅收缩」护栏**（可用 `SYNC_SHRINK_GUARD` 环境变量控制）——节点数大幅减少时拒收，并打一行摘要日志说明少了什么。
4. **CAS 乐观锁**——`SaveSyncDataIfUnchanged`，版本令牌用纳秒精度时间戳。版本不符时返回 `conflict: true`，让客户端重拉重试，**而不是覆盖**。

> 🔴 **为什么必须是 CAS**：画布是整块 JSON 覆盖写的。没有 CAS 的话，「读取—修改—写回」之间的并发编辑会被整块回滚掉，而且**没有任何报错**——用户只会发现自己刚才画的东西没了。
>
> 任何绕过 `SaveSyncDataIfUnchanged` 直接 UPDATE `sync_data` 的代码都是数据丢失事故的种子。

写入时还会调 `captureSnapshot` 存历史快照，这是画布误删后唯一的恢复来源。

### 3.2 媒体资源与「自愈」

画布上的图片/视频有一套自愈逻辑：资源加载失败时，不是直接显示破图，而是拿 `storageKey` 去服务端重新换一个可用地址。

**为什么需要它**：浏览器的 `blob:` URL 会被持久化进节点数据，但它换域名、刷新页面后就失效了。没有自愈的话，用户的画布会在某次刷新后大面积变成破图。

自愈分两级：

1. 一级：`content` 取不到 → 用 `storageKey` 向服务端要地址
2. 二级：本地 IndexedDB 里的缓存本身是坏的 → 删掉本地条目，强制向服务器重拉一次

> ⚠️ 只有一级自愈时会出现一个隐蔽故障：坏的本地缓存被一级自愈「命中」，生成一个看似有效、实际打不开的链接，第二次加载失败就被判死。二级兜底就是为这个加的。

## 四、生成链路

### 4.1 三条链路的形态

| | 图片 | 视频 | 音频 |
|---|---|---|---|
| 同步/异步 | 异步 job | 异步 task | 同步 |
| 谁执行 | 后台 worker goroutine | 提交后由客户端轮询 + 后台扫描器兜底 | 请求内完成 |
| 计费 | 预扣 × 张数，**少出图退差额** | 预扣（按选定秒数） | **预扣 + 按实际时长结算** |
| 失败退款 | worker 内 `refundForJob` | 扫描器 / 启动恢复 / 客户端认领 | 结算时多退少补 |

### 4.2 视频：为什么这条链路这么复杂

视频是提交/轮询分离的，**客户端随时可能关掉页面**。于是系统必须自己记住每一单：

- 提交那一刻就把 `canvasId` + `nodeId` + 位置尺寸记进退款候选表
- 后台扫描器定时查上游状态：失败的退款，成功但没送达的**直接写回画布节点**（或放进「我的素材」）
- 进程被杀时可能有「已扣费、还没拿到上游任务号」的单子卡在半路——这笔钱没有任何机制按任务号去退，所以**启动时**专门有一步把这类占位候选找出来退掉

> 这一整套机制存在的唯一理由是：**没有任何一个时刻能保证「上游成功了、而且我还活着可以去处理」**。

### 4.3 并发与闸门

图片生成 worker 的并发槽位由环境变量控制，改 `.env` 重启即可调整。用量上来之后如果出现「排队十几分钟」，先看这个值。

画布助手（会自己循环调模型的那个）另有两道闸：轮次闸和单回合预算闸，**都在扣费之前**。

## 五、计费：这套系统最危险的部分

> 动任何与钱有关的代码之前，请把这一章读完。

### 5.1 一律预扣，绝不后扣

三条链路的扣费**全部发生在调用上游之前**。

扣费之前还有四道「不花钱就拒绝」的闸，顺序本身就是设计：

1. 画布助手轮次闸——「被闸住的请求一分钱都不该花」
2. 画布助手单回合预算闸——此时 credits 刚算完、还没扣
3. **视频编辑的计费秒数探测失败 → 直接拒绝**——「一分钱都还没扣，直接拒绝即可，不存在要退的钱、也不会留下待退款的孤儿记录」
4. 人像资产前置校验——「命中就直接拒绝，压根不扣，而不是扣了再退」

### 5.2 余额不足拦在哪

拦在扣费函数本身，靠**数据库原子条件**：

```sql
UPDATE users SET credits = credits - ? WHERE id = ? AND credits >= ?
```

`RowsAffected == 0` 即余额不足。**这是唯一能防并发透支的地方。**

项目积分池同理。命中项目但池子不足时报「项目积分不足」，**不回退个人积分**。

### 5.3 🔴 如果你想改成「后扣」——不要

代码里读得出四条理由：

1. **原子性**：余额校验和扣减必须在同一条 SQL 里。改成后扣，「查余额」和「扣钱」之间必然有窗口，同一用户并发发 N 个请求就能把余额扣成负数。
2. **异步链路上没有可靠的执行时机**：视频提交/轮询分离、客户端随时可能关页；图片 worker 在独立 goroutine 里跑、进程可能被杀。没有任何一刻能保证「上游成功了、而且我还活着」。
3. **闸门语义**：预扣让余额成为真正的闸；后扣时闸只能靠估算，失控时钱已经花出去了。
4. **退款基础设施已经围绕预扣建好了**：单事务退款、启动恢复、后台补退——预扣 + 失败退款只需要保证「退款幂等」这一件事，而幂等比「保证一定执行」容易得多。

### 5.4 图片：单价快照

图片预扣 `单价 × 请求张数`，成功后比对上游实际产出的张数，少出几张按**下单时落在 job 行上的单价快照**退差额。

> ⚠️ **为什么必须用快照而不是重新查价**：事后重新查价既不知道当时选的哪一档，也可能查到管理员中途改过的新价。加任何新的计价维度时，记得同步把它存进 job 行。

### 5.5 ⭐ 音频：预扣 + 结算，以及为什么补扣必须允许扣成负数

**这是整套计费里最微妙的一条，也请重点理解。**

音频按秒计价，但**上游没有时长参数**——真实秒数只有出片后才知道。所以不能像视频那样一次扣准，只能：

```
预扣（默认 15 秒）→ 出片 → 按上游返回的真实时长结算差额（多退少补）
```

秒数归一：`<= 0` 用默认 15 秒，超过 120 秒钳到 120（上游硬上限）。不足 1 秒按 1 秒算（0.4 秒的音效也得收钱）。

**关键问题：补扣时余额不够怎么办？**

第一版实现走的是普通扣费函数，余额不足就返回错误、调用方只打一行日志。这是个**可被反复利用的白送漏洞**：

> 音频**已经交付给用户了**。此时「余额不够就放弃扣费」= 平台白送。
> 而且预扣额完全由客户端控制、与产出无因果关系：
> 预扣按 15 秒，提示词里写「生成一段两分钟的雨声」——
> 于是每次只需 15 秒的余额，就能换 120 秒的产出，**可以无限重复**。

**正确做法**：结算补扣走一个**不校验余额**的专用路径，允许把余额扣成负数。

```go
// 与普通扣费唯一的区别是【不校验余额】，允许把余额扣成负数。
//
// 产物已经交付到用户手里了，这时候「余额不够就不扣」等于平台白送。
// 让余额变负是唯一诚实的记法：账面如实反映欠了多少，而扣费入口的
// `credits >= ?` 会自然把后续生成挡住，直到充值补平。
//
// ⚠️ 只给结算用。任何「先付费后交付」的路径都必须继续走普通扣费函数。
```

**闭环论证**：余额变负之后，普通扣费入口的 `WHERE credits >= ?`（成本恒 > 0）必然不匹配 → 后续一切生成被拒。**所以透支最多发生一次**，单次最大透支额 = `(120 − 15) × 每秒单价`。

> 💡 这条设计给二次开发的启示：**任何「先交付、后结算」的新功能都会有同样的敞口**。要么照搬这套「允许扣负 + 靠扣费入口自限」的模式，要么就别做成先交付后结算。

顺带一提，`repository/user.go` 里维护着一份 **`credits` 列的「唯一合法写入方」清单**（注释形式）。新增任何会改 `credits` 的函数，请同步登记进去——这份清单是排查「钱对不上」时的第一现场。

### 5.6 🔴 改定价的三个陷阱

**陷阱一：某档没配价会静默回退，且前后端一致地错**

视频按分辨率档配价。某一档没配单价时，系统会回退到「720p 档 → 第一条费率」，**并且返回「命中」**。

后果很具体：放开 1080p/4K 却没配该档单价 → 系统**按 720p 的单价收高清片的钱**，前后端显示与实扣完全一致，流水里没有任何异常痕迹，只能靠对账发现。

> **所以：放开任何新档位之前，必须先配好该档单价。**

**陷阱二：前端显示价与后端实扣是两份独立实现**

价格估算在前端（决定显示）和后端（决定实扣）各有一份归一化函数，必须逐分支对齐。代码注释里记载过一次 **5 倍差价** 的事故。

**当前存在一处客观分叉**（见第十章已知问题）。

**陷阱三：退款用的是下单时的价，不是当前价**

见 5.4。改价格结构时，注意所有「事后退款」路径用的都应该是快照。

## 六、视频生成模式

这是最值得先读的一章——它替换掉了一套**在真实场景下会猜错**的旧逻辑。

### 6.1 它解决了什么问题

视频生成有好几种玩法：纯提示词出片、拿一张图动起来、给首帧和尾帧让它补中间、把素材当内容参考（人物/场景/风格）、改写一段已有视频、把已有视频续写下去。

**旧做法是按「用户接了几个素材」去猜的**：

| 素材数量 | 猜成什么 |
|---|---|
| 0 个 | 文生视频 |
| 1 个 | 图生视频 |
| 2 个纯图片 | **首尾帧** |
| 3 个及以上 | 参考生视频 |

这套推断的问题不是"不够保守"，是**在常见用法下直接错**：

> 用户接了一张场景图 + 一张人物图，想做「参考生视频」——让模型参考这两张图的内容生成一段视频。
> 按数量推断，这被判成**首尾帧**，也就是"从场景图渐变到人物图"。
> 生成语义整个错掉，输出比例也跟着首帧走，而钱照扣。

更糟的是用户**无从察觉**：界面上没有任何地方显示系统把这一单理解成了什么。

### 6.2 现在有哪几种模式

模式清单定义在 [`web/src/lib/seedance-video.ts`](../web/src/lib/seedance-video.ts) 的 `VIDEO_MODES`：

| 模式 | 值 | 什么场景 | 素材要求 |
|---|---|---|---|
| 文生视频 | `text_to_video` | 纯提示词出片 | 不能接任何素材 |
| 图生视频 | `image_to_video` | 用 1 张图作首帧动起来 | 1 张图 |
| 首尾帧 | `first_last_frame` | 1 张=只定首帧；2 张=首帧+尾帧 | 1–2 张图 |
| 参考生视频 | `reference_to_video` | 把素材当**内容**参考（人物/场景/风格），不是帧 | 至少 1 个素材 |
| 视频编辑 | `video_edit` | 改写已有视频（增删改画面元素） | 1 段视频 |
| 视频延长 | `video_extend` | 把已有视频向前或向后续写 | 1 段视频 |

还有一个 `auto`，它是**存量取值**，界面上已经不再是可选项（`hidden: true`）。它的语义正是"不声明任务类型、让上游自己推断"——那恰恰是本轮要根治的东西。代码保留它只为认得出老数据。

> ⚠️ **`video_edit` / `video_extend` 依赖上游的 `omni_reference_task_type` 字段**，只有支持该字段的模型才有这两档。见 6.5。

### 6.3 模式是怎么决定的（重要的行为约定）

决策函数 `resolveVideoModeForCounts()`，规则**只有三条**：

```
① 一个素材都没有       → 文生视频
② 有素材 + 用户显式选了 → 原样不动
③ 有素材 + 其余一切取值 → 参考生视频
```

第 ③ 条覆盖了 `auto`、空值、拼错的值，以及"接了素材之后已经不成立的文生视频"。

**"显式模式"指这四档**（常量 `VIDEO_MODES_EXPLICIT`）：图生视频、首尾帧、视频编辑、视频延长。它们与"参考生视频"是不同的生成语义（把图当帧 vs 把图当内容参考），只可能是用户自己点出来的，所以系统一个字都不会替他改。

`text_to_video` **故意不在**这个名单里：它是"没有素材"时的默认值，接了素材就说明它已经不成立了。

两个必须保持的性质：

1. **幂等**：`resolve(resolve(x)) === resolve(x)`。调用点都是"算出来不一样就写回去"的写法，不幂等会变成写回→重算→再写回的死循环。
2. **返回值一定是当前模型支持的模式**。否则会出现"界面显示的和实际发出去的不是一回事"。

### 6.4 请求层的闸门：为什么有两个 resolve 函数

`resolveVideoModeForRequest()` 在 `ForCounts` 之上加了一道闸门，**存在的全部理由是：素材不满足时抛错，而不是静默落回**。

静默落回长什么样：

> 用户选了「图生视频」，随后把参考图从 1 张接成 2 张。按钮上仍然写着「图生视频」，
> 请求层却把模式悄悄换掉再发出去。

那是旧毛病换个楼层重演——入口从"让上游猜"变成"前端先把用户的声明扔掉、再让上游猜"。用户看到的和系统做的是两件事，且没有任何提示。

**闸门只对用户自己点出来的模式生效，不对推导出来的生效。** 这个区别是测出来的，不是想出来的：最初写成"对落定后的模式一律校验"，结果那些不支持「参考生视频」的第三方视频模型一接参考图就抛错——而它们**改动前是能用的**（参考图照发，用不用由上游决定）。那等于凭空加了一条上游根本没要求的限制。

所以最终行为是：

- 用户**没点过** → 推导出什么就发什么，绝不拦
- 用户**点过**图生/首尾帧/编辑/延长而素材不满足 → 抛出一句现成的中文原因，让他自己决定改素材还是改模式

> 正常情况下这里抛不出来：界面已经按同一套判据把不可选的模式灰掉并写明原因了。
> 它拦的是竞态、老客户端、以及界面与请求层口径万一分叉的情况——
> 那种时候宁可当场失败，也不要发一个用户没选过的任务出去（照样扣钱）。

### 6.5 `omni_reference_task_type`：为什么参考生视频也要显式声明

这是上游的顶层字段（与 ratio / duration 平级），取值 `reference` / `edit` / `extend`。函数 `seedanceOmniTaskType()` 决定这一单带不带、带什么。

**为什么"参考生视频"也要显式发 `reference`**，而不是省略让上游默认：

> 上游文档说，不发这个字段时模型会**按提示词意图**自行判定成参考生视频/编辑/延长。
> 而编辑和延长都有「比例必须 adaptive」的硬约束。
> 用户在参考生视频里写一句「把背景改成夜晚」，就可能被判成**编辑**，
> 然后因为我们发的是 16:9 而**异步报错**——那时钱已经扣了，用户只看到一句英文错误。

显式发 `reference` 把任务类型钉死。**这一步只锁定、不改行为**：上游文档里参考生视频的官方示例配的就是 `ratio: 16:9`，与现状一致。

> ⚠️ **这个字段只发给支持它的模型系列。** 给不认识它的模型多发一个顶层字段，可能整单被拒。
> 代码里用 `isSeedance25Model()` 判定，不支持的模型上选参考生视频**仍然不带这个字段**——存量请求形态一个字节都不动。

### 6.6 编辑与延长的计费

这两档的计费和别的模式不一样，是**这一章最需要小心的地方**。

**视频延长**：上游的 `duration` 是**输出总长**，不是增量。实测 4.06 秒的源视频、`duration: 6`，出片正好 6.00 秒。所以按用户选的秒数扣费是对的，无需特殊处理。

**视频编辑**：上游**要求 `duration: -1`**（由模型自己决定，实测输出时长等于源视频时长）。这就带来一个计费问题——按秒计价的模型，`-1` 秒怎么扣？

系统的做法是**服务端探测源视频的真实时长**（ffprobe，只读文件头），按真实时长计费。

> 🔴 **探测失败时是直接拒绝，不是回退到默认值。** 这一条务必保持。

> 💡 **界面上不显示预估数字。** 视频编辑模式下，生成按钮上的位置显示的是「按源片时长」而不是一个数。
>
> 因为面板这一层**拿不到源视频的秒数**——节点引用结构里只有 id/种类/标签/预览图，没有时长；
> 而且浏览器读不出 H.265 时，时长要等服务端探测回填，那一刻根本没有可信值。
> 照常按用户选的秒数算，就会显示一个**必然错**的数字（选 6 秒、源片 22 秒 → 显示 6×单价、实扣 22×单价）。
> 与其显示一个有时准有时错的数，不如显示计费口径本身。
>
> ⚠️ 两个面板（提示词条、配置节点）的判据必须一致，否则同一单在两处显示不同。

>
> 配置里有一个"智能时长"的默认秒数，`seconds <= 0` 时会落到它。如果探测失败后放任 `-1` 流下去，
> 就会按那个默认值扣费——**一段 4 秒的视频按默认值收钱，或者一段 30 秒的视频只收默认值**，
> 两个方向都是错的，而且日志上看不出异常。
>
> 拒绝发生在扣费**之前**，所以失败的单子不会扣钱。

### 6.7 界面上怎么呈现

模式选择器与分辨率、比例、时长等合并在**同一个可展开的设置面板**里，不展开也能看到关键信息。鼠标悬停每个模式会显示该模式需要几个素材。当前素材不满足的模式**灰掉并写明原因**——和请求层用的是同一套判据（`videoModeAvailable()`），保证"看到的就是发出去的"。

面板的宽度和提示词框高度可以在偏好设置里调整（配置项 `canvasPanelWidth` / `canvasPanelPromptHeight`），通过 CSS 变量下发，不走状态订阅——因为节点组件是逐节点渲染的，订阅会破坏 memo。

### 6.8 模式与模型能力的关系

不是所有模型都支持所有模式。`videoModeSupportedBy(model)` 给出某个模型支持的模式清单。走通用 OpenAI 方言的第三方视频接口通常只有"文生"一档。

对这类模型：

- 界面上其余模式**灰掉**
- 即使配置里存着一个它不支持的模式值，`resolveVideoModeForCounts` 也会把它归一掉
- 但**不会**因此拒绝请求（见 6.4 的教训）

## 七、数据模型

### 7.1 表与自动迁移

启动时 `AutoMigrate` **24 张表**，首次启动自动建，不需要跑任何迁移脚本。按职责分四类：

- **核心业务**：用户、点数流水、提示词、素材、画布同步数据、画布快照、同步文件、画布分享
- **组织**：分组、项目、项目成员、团队素材、团队风格
- **任务与计费**：图片生成任务、视频退款候选、上游日志、Token 日志、媒体转码任务
- **辅助**：系统设置、人像资产、短信日志、用户反馈、提示词收藏、用户操作审计

> ⚠️ **AutoMigrate 只加不删**：新增字段会自动建列，**删除字段不会删列**，改类型也不一定成功。生产库上做破坏性变更必须手写 SQL。
>
> ⚠️ **日志类表会长得很快**（上游日志、Token 日志、点数流水、审计日志）。这几张表没有内置清理机制，需要自己规划归档策略。

### 7.2 用户 / 分组 / 项目 / 积分

三级隔离：

- **用户**属于一个**分组**，分组决定他能用哪些模型渠道、用哪个存储桶
- **项目**是独立的积分池，用户可以是多个项目的成员
- 请求带 `X-Project-ID` 且用户是该项目成员且项目是 active → **扣项目池**；否则扣个人余额

> ⚠️ 命中项目但池子不足时报「项目积分不足」，**不会回退去扣个人积分**。这是有意设计。

权限分三级：普通用户 / 二级管理员 / 超级管理员。二级管理员只能看到自己名下的分组与用户，隔离规则写在 `handler/auth.go`（不在 service 层）。

### 7.3 🔴 文件存储：换存储会不会让老数据失效

**会，而且是静默失效（死链，不报错）。** 但大部分可以批量修。

存储有三种落点，按优先级：对象存储（S3 协议兼容）→ 本地磁盘 → （前端 IndexedDB 只是缓存，不是权威副本）。

关键在于**数据库里存的是完整 URL，不是 key**。以最大的那张同步文件表为例，它有两列：

| 列 | 存什么 |
|---|---|
| `storage_key` | **逻辑键**，形如 `image:abc123`，前端生成，与存储后端无关 |
| `path` | **完整公网 URL 或服务器本地绝对路径**，二选一 |

读取时按 `path` 前缀判断：`http://` / `https://` 开头就 302 跳过去，否则当本地路径打开。

**换桶之后怎么修**：对象键是**确定性函数** `f(user_id, storage_key, mime_type)`，这三个输入**都在表里**。所以：

1. 把旧桶对象按同样的 key 路径复制到新桶
2. 对该表跑一条 `UPDATE`，把 `path` 里的域名前缀换掉

不需要重新上传，也不需要改前端。

> 🔴 **但落在本地磁盘的那些行修起来麻烦得多**：它们的 `path` 是绝对路径（如 `/app/data/sync-files/...`），换了数据目录或换台机器就全断，代码里**没有**「按当前数据目录重新拼路径」的兜底。
>
> **建议：一开始就配好对象存储，不要让数据落本地磁盘。**

另外，分组可以配自己的桶。组的桶配置非空时**整体使用组凭证**，此时 AK/SK/公网域名缺任何一项都会直接报错，**绝不静默回退到全局桶**——这是防止跨组数据写混的有意设计。

## 八、二次开发手册

### 8.1 改品牌名

产品名默认是「FrameWeave」，取值优先级（就近覆盖）：

1. 构建环境变量 `NEXT_PUBLIC_APP_NAME`（适合 CI；容器构建需作为 build arg 透传）
2. `web/APP_NAME` 文件（改一个文本文件就行，随源码进镜像）← **推荐**
3. 代码默认值

> 🔴 **`NEXT_PUBLIC_*` 是构建期内联的**：Next 打包时把取值直接写进产物，**运行时再改环境变量不会有任何效果**。改完名字必须重新构建前端。

除了上述三处，还有几个地方硬编码了品牌名或其拼音，**换品牌时按需一并改**：

| 位置 | 是什么 | 改了会怎样 |
|---|---|---|
| `web/src/constant/env.ts` | 前端应用名回退值 | 显示用 |
| 部署脚手架的 compose 项目名 / 网络名 / 镜像仓库名 / 数据目录 | 部署标识 | 改名要连带改 compose 配置 |
| `web/src/app/(user)/canvas/[id]/canvas-client-page.tsx` 的剪贴板标记常量 | 画布复制粘贴的识别前缀 | **改了之后旧剪贴板内容粘不进来**，但只影响当次会话 |
| `web/src/services/file-storage.ts`、`web/src/stores/use-user-store.ts` 的自定义事件名前缀 | DOM 事件名 | **必须与所有 `addEventListener`/`dispatchEvent` 成对改**，改漏一半会导致视频元信息/预览/积分刷新静默失效 |
| `deploy/docker/*.Dockerfile` 的基础镜像名 | 构建参数默认值 | 改名要同步改 `deploy.sh` |

这些都不是敏感信息，是产品默认标识。**完全换皮时建议全局搜索一遍再改**，特别是那两组事件名——它们改漏了不报错。

### 8.2 产品内「更新说明」弹窗

根目录的 `CHANGELOG.md` **是构建输入**：`web/next.config.ts` 解析它、注入前端，作为产品内「更新说明」弹窗的内容。

格式约定（不合格式的行不会显示）：

```
## <版本号> - <日期>
+ [类型] 正文
```

> ⚠️ 发新版本时记得更新它，否则用户在弹窗里看到的还是上一版的说明。同理，`VERSION` 文件的内容也会注入前端。

### 8.3 接入一个新的 AI 模型

**先记住三件事：**

1. **模型名不在代码里**，在数据库的系统配置 JSON 里。
2. **用户能看到的模型列表来自他所属分组的渠道**，不是全局列表。全局列表只是没配分组渠道时的兜底。
3. **「这个模型是什么类型」有两套判据**：后台配置的模型元信息（优先）和硬编码的名字关键词表（回落）。

**步骤：**

| 步 | 做什么 | 在哪 |
|---|---|---|
| 1 | 把模型名挂到渠道上（**必做**） | 后台「分组管理 → 编辑分组 → 模型渠道」 |
| 2 | 标类型和可用档位（强烈建议） | 后台「系统 → 分级定价」最上面那张表 |
| 3 | 配价（视频必须**逐档**配，见 5.6） | 同上 |

第 1 步的模型名和渠道模型列表里的字符串必须**一字不差**——路由时按模型名精确过滤候选渠道。

第 2 步不标也能跑：后端每次启动会按名字关键词猜一个类型写回去，**只增不改**，手工标过的不会被覆盖。但猜错了就得手工纠正。

**要不要发版：**

| 新模型的情况 | 只改数据库够不够 |
|---|---|
| OpenAI 兼容的文本 / 图片 / 音频模型 | **够**，后台配完即生效 |
| 名字不含常见视频关键词的视频模型 | **够**，但必须手工标成 video，否则前端视频下拉里看不到它 |
| 某个视频模型系列的**新代次**（新能力/新档位/新时长上限） | **不够，必须改代码重新构建前端**——能力表是硬编码的，见第九章第 4 条 |

### 8.4 接入一个新的上游渠道

> 🔴 **先说最重要的一点：当前版本没有「协议」这层抽象。**
>
> 渠道有个 `Protocol` 字段，但全后端只有两处读它，都只是把空值填成 `"openai"`，**没有第三个读取点**；前端下拉也只有「OpenAI 兼容」一个选项。**它是个占位字段。**

真正决定「请求怎么发」的是**四类散落的判据**：

1. **baseURL 结尾**——决定自动补不补 `/v1`
2. **baseURL 域名**——特定云厂商走特定分支
3. **模型名**——若干 `isXxxModel` 函数
4. **环境变量白名单**——按上游域名片段决定某些字段的发送形式。这是唯一一个「为特定中转站开后门」的正规入口，改 `.env` 重启即可，不用改代码

所以接一家请求形态不同的供应商时，**没有一个「实现这个接口即可」的扩展点**，必须挨个找上面这些判据各加一条分支。完整清单见第九章第 5 条。

渠道还有个为 AK/SK 双段凭证预留的字段，但**当前版本没有任何读取方**。

> ⚠️ 渠道的 `ID` 字段是用量埋点的归集键。后台表单里是隐藏字段，**删掉会导致每次保存都重铸新 ID，历史用量散在一串死 ID 上**。

### 8.5 在画布上加一种新节点类型

节点类型是个前端枚举（现有 9 种）。加一种要改这些地方，**按顺序**：

| # | 位置 | 漏了会怎样 |
|---|---|---|
| 1 | 类型枚举 | — |
| 2 | 默认尺寸 + 规格表 | **TS 直接报错**（编译器帮你兜住） |
| 3 | 中文名标签表 | 🔴 **不报错**，节点名显示成「节点1」 |
| 4 | 节点渲染的组件映射表 | 渲染不出来 |
| 5 | 小地图颜色 | 🔴 **不报错**，小地图上是一块灰方块 |
| 6 | 创建菜单的回调联合类型 | 菜单里没有入口 |
| 7 | 节点工厂函数 + 默认比例 | 建出来的节点缺字段 |
| 8 | hover 工具栏 | 按需 |
| 9 | AI 助手可操作性 | 助手建的节点缺命名序号 |

> 🔴 第 3、5 两处**没有类型兜底、漏了不报错**，要靠人眼发现。

**序列化 / 同步不用改**：画布数据以整块 JSON 存储，同步层对节点类型完全无感知，新类型的 metadata 会原样往返。

> ⚠️ 但如果新节点要挂媒体文件，**必须走上传接口拿 `storageKey`，不能把 base64 直接塞进节点内容**——那会让画布 JSON 迅速膨胀，撞上同步体积闸。

### 8.6 本地开发（不用 Docker）

**前置**

- Go 1.25+
- Node 22 / Bun（`bun.lock` 和 `package-lock.json` 都有，npm 也能装）
- 🔴 **ffmpeg / ffprobe 必须在 PATH 上**——视频探测和转码直接调这两个二进制。缺了不影响启动，但**视频编辑会直接拒绝提交**、转码会失败
- **数据库可选**：本地开发可以不装 PostgreSQL，用 SQLite 即可

**后端**

在仓库根目录建 `.env`：

```
STORAGE_DRIVER=sqlite
DATABASE_DSN=data/aicanvas.db
ADMIN_USERNAME=admin
ADMIN_PASSWORD=<自己设>
JWT_SECRET=<固定写死一串>
PORT=8080
PUBLIC_BASE_URL=http://localhost:3000
```

然后 `go run .`。建表自动完成，不用跑迁移脚本。启动每一步都有耗时日志，卡住时一眼能看出卡在哪。

**前端**

```
cd web
bun install
API_BASE_URL=http://127.0.0.1:8080 bun run dev
```

浏览器只打自己的同源 `/api/*`，由 Next 的 catch-all 路由转发到后端。

**热重载**：前端自带 HMR；**后端没有内置热重载**，自己装 `air` 或每次重跑。

**三个必踩的坑**

1. 🔴 `JWT_SECRET` 留空 = 每次重启随机生成 = 所有登录态作废
2. 🔴 `ADMIN_PASSWORD` 留空 = **不创建任何管理员**，服务照常起、页面照常开，但没人能登录后台
3. ⚠️ `NEXT_PUBLIC_*` 构建期内联，改了必须重新构建

## 九、🔴 散落多处的逻辑：改一处会漏的地方

> **这一章是本文档最重要的部分。**
>
> 下面每一条都是「同一件事在代码里有多份实现」。它们的共同特征是：**改漏了不会报错，而是产生静默错误**——功能看起来好的，行为却不对。

### 9.1 「这个模型是什么类型」

判据分布在**后端 5 处 + 前端 7 处**，其中前后端各有一份**必须逐字一致**的关键词表。

后端启动时会把自己的判定写进模型元信息，而各读取点读元信息的优先级**高于**名字关键词。

**后果**：后端关键词表少认一个词 → 启动回填把该模型永久写成错误类型 → 它从对应的模型下拉里消失、并且在定价页被归进错误的表（视频模型永远配不了分辨率价），**管理员看不出原因**。

> ✅ **本版本已加防线**：前后端关键词表抽成了唯一数据源（`service/model_kind_rules.go` 与 `web/src/lib/model-kind-rules.ts`），并用共享的 fixture 对拍。**两个 Dockerfile 在构建时强制跑这个对拍**，任何一边改了关键词而另一边没跟上，**构建当场失败**。
>
> ⚠️ 所以：改关键词表必须**两边一起改**，并把新模型名补进 fixture。不要删掉 Dockerfile 里那两条 `RUN`。

### 9.2 上游鉴权头

`Authorization: Bearer <key>` 被复制了 **6 份**，没有任何统一入口：主代理、视频轮询代理、后台扫描器、拉取模型、测试连通、图片任务 worker。

**后果**：接一家不用 Bearer 的供应商时，改漏任何一处的表现都不同——

- 漏 worker → 图片全失败
- 漏扫描器 → **失败视频永远不退款，且无人察觉**
- 漏「拉取模型 / 测试连通」→ 后台永远红叉，但生成其实是好的，**会把人引向完全错误的排查方向**

### 9.3 画布节点配置的字段映射

节点 metadata ↔ 生成配置的映射被**手写复制 4 份**，外加 3 处生成后回写、2 份键名翻译函数、1 处空串兜底。

**后果**：新增一个节点配置字段漏改其中任一处，症状不是「用不了」而是**「点了没反应」**——面板选中态读配置、写的却是节点 metadata，两边不接通就永远读不回来，请求里一直是默认值，**且不报任何错**。

> 💡 加任何节点配置字段时，先全局搜索一个现有字段名，看它出现在几个地方，然后**每一处都照着加**。

### 9.4 视频模型的能力表有两个来源

- **后台可编辑的模型元信息** → 只管界面灰选
- **前端硬编码的能力表** → 管请求层钳位和价格估算

**后果**：管理员在后台把某模型最长秒数改成 30，界面滑杆真能拉到 30，但请求层仍按硬编码表钳到 15、价格也按 15 算——**用户选了 30 秒、看到 15 秒的价、拿到 15 秒的片，三方各说各话**。分辨率档同理。

### 9.5 「请求该怎么发」的判据

散在四类来源里（详见 8.4），共 10 处左右。

**后果**：漏掉前端那份判据的典型症状是——后端已经支持、但前端仍按旧方言拼请求体，**报错来自上游**，看不出是自己少改了一处。

### 9.6 分辨率 / 画质档的归一化

前端（决定**显示价**）和后端（决定**实扣**）各一份，必须逐分支对齐。

**代码注释里记载过一次 5 倍差价的事故。**

> 🔴 **当前存在一处客观分叉**，见第十章。

### 9.7 某档没配价时的静默回退

前端、后端、后台定价页**各实现一遍同一套回退**（精确档 → 720p 档 → 第一条费率），三处一致地错。

**后果**：见 5.6 陷阱一。

另一个同源的坑：一个模型**在所有价格表里都没配**时，最终按次价取到 0，扣 0 点、不报错、也不记流水——
等于这个模型对所有人免费，而上游照常向运营方计费。加新模型时务必先配价。

### 9.8 节点类型的登记点

见 8.5。其中中文名标签表和小地图颜色**没有类型兜底、漏了不报错**。

## 十、已知问题与限制

### 10.1 分辨率归一化的前后端分叉（会影响显示价）

前端和后端对「像素串 → 分辨率档」的判据不一致：

| 短边像素 | 后端判为 | 前端判为 |
|---|---|---|
| ≤ 560 | 480p | 480p |
| ≤ 900 | 720p | 720p |
| 901 – 1200 | 1080p | 1080p |
| **1201 – 1980** | **1080p** | **2160p** ← 分叉 |
| > 1980 | 2160p | 2160p |

**影响**：传形如 `1440x1440` 这类**像素串**时，前端显示 2160p 的价、后端按 1080p 扣。方向上是「显示偏贵、实扣偏便宜」。

**限定**：画布主路径传的是**档位名**（如 `1080p`）而不是像素串，所以常规操作不一定会走到这个分支。**但改动档位逻辑时两边必须一起核。**

修的时候要先定一个产品决策：短边 1440（2K）这类尺寸应该归 1080p 还是 2160p——系统只有四档，2K 没有对应档位。

### 10.2 没有协议抽象层

见 8.4。`Protocol` 字段是占位符，接新供应商需要在四类判据里各加分支。这是本版本最大的扩展性欠账。

### 10.3 分层不完整

同步、项目、分组、用户反馈、画布快照这几大块没有 service 层，业务规则写在 handler 里。另有一个后台协程住在 handler 包。见 2.3。

### 10.4 日志类表无清理机制

上游日志、Token 日志、点数流水、审计日志会持续增长，需要自己规划归档。

### 10.5 同一视频模型挂在多个渠道上：查询会选错渠道

选渠道只看模型名，按权重随机挑。提交和查询是两次独立的挑选，**系统没有记住任务是在哪个渠道上提交的**。
同一个视频模型挂在两个渠道上时，查询可能落到另一个渠道，对方查不到这个任务号、返回 4xx，
代理层据此判定失败并退点——而任务可能仍在原渠道正常生成。兜底扫描同样按模型名重新挑渠道，有同样的问题。

规避：同一个视频模型名只挂在一个渠道上。根治需要在提交时记下渠道（`upstream_logs` 已有 `channel_id` 字段可用），
查询和兜底扫描优先回到原渠道。

### 10.6 已知安全问题（待修复）

下列问题在当前版本已知存在、尚未修复。都要求先登录才能触达；把 `allowRegister` 关闭且不开放短信 / 第三方登录时，只有管理员建过账号的人可利用。面向用户的缓解建议见 [SECURITY.md](../SECURITY.md)。

**计费可被重复字段绕过。** 提交视频生成时，计费值由后端用 `encoding/json` 解析请求体得到（`handler/ai.go` 的 `readAIVideoBilling`）。Go 解析 JSON 键名不分大小写、且后出现的同名键覆盖前面的；若上游按大小写敏感、或取首个同名键解析，二者就会分叉，导致按较小的时长 / 分辨率计费、却按较大的实际执行。扣费发生在调用上游之前，差价由运营方承担。修复方向：计费前拒绝顶层对象里存在重复键（含仅大小写不同）的请求，用流式 `json.Decoder` 遍历检测（`map` 反序列化会把重复键吞掉）；正常前端请求不含重复键（见 `web/src/services/api/video.ts`）。

**服务端拉取用户地址时内网过滤不完整（SSRF）。** 两条路径会由服务端去访问用户提供的地址：

- 视频编辑按源视频时长计费——`handler/ai.go` 的 `videoEditBillingSeconds` → `service.ProbeVideo`（`service/media_probe.go`）只校验了 `http(s)` 前缀就交给 `ffprobe`，而 `ffprobe` 会自行跟随跳转，没有任何内网拦截。属半盲 SSRF：拿不回内容，但能探内网端口、从报错与耗时推断。
- 媒体转存——`handler/media_persist.go` → `SafeHTTPClient`（`service/safe_http.go`）。它在拨号阶段按真实 IP 拦截（可防 DNS rebinding 与跳转），但 `isBlockedIP` 漏了 `100.64.0.0/10`（CGNAT，部分云厂商的实例元数据服务在此段）。该接口会把拉到的字节存进桶并返回地址，因此可能被用来读回内容。

修复方向：给 `ProbeVideo` 加同一套地址校验（`ffprobe` 自行拨号、Go 的 `Dialer.Control` 管不到它——可先用 `SafeHTTPClient` 取字节再喂给 `ffprobe`，或钉住解析后的 IP 并禁跳转）；补全 `isBlockedIP` 的非公网网段（`100.64.0.0/10`、`0.0.0.0/8`、`169.254.0.0/16`、IPv4 映射的 IPv6 等）。部署方在修复前可限制后端出网、屏蔽实例元数据地址、给实例用 IMDSv2 或不绑高权限 IAM 角色。另参见 9.2（漏扫描器导致失败视频不退款）与 10.5（多渠道误退款），它们同样涉及计费正确性。

### 10.7 需要自行验证的部分

部署测试验证到「装得起来、能登录、代码在镜像里、构建期对拍通过」。

**真实生成未验证**——需要配置上游渠道密钥才能跑通，而密钥属于各自账号、不随源码提供。**请在配好自己的 key 之后，自行验证一遍真实生成效果。**

## 附：代码注释的价值

这套代码的注释密度远高于一般项目，很多函数上方有长注释记录「为什么这么写」以及曾经发生过什么。**建议保留它们**——那是这套代码最有价值的部分之一，删掉等于把踩过的坑重新埋回去。

典型例子（都在本文档里引用过）：

- 为什么补扣必须允许扣成负数
- 为什么画布同步必须用 CAS
- 为什么扣费必须在调用上游之前
- 为什么参考生视频也要显式声明任务类型
- 为什么模式闸门只对用户显式选择生效

阅读代码时，**先读注释再读实现**，能省掉大量猜测。
